# StarBegonia 项目设计

家庭收支与分摊管理系统：把各平台账单统一进来，按来源设定 AA 规则，可视化汇总，并完成结算。

---

## 1. 目标

- 自动或半自动从多种来源收集家庭开销与收入流水
- 对多来源数据进行整合与可视化
- 按账单来源组合设定 AA 规则，并在结算中心完成「谁欠谁多少」
- 为后续 AI Agent（如购物清单）预留能力入口（MCP），Agent 本身不在本项目范围

本期明确不做权限体系；投资模块与 MCP 放在后期。

---

## 2. 核心概念

### 2.1 数据源（Source）

账单从哪里来。每种来源有统一的「接入方式」，具体平台各自实现。

**前期：**

- 手动录入
- Coles（超市源；具体拉取/解析由实现方自行完成，设计上保留接入位置）

**后续：**

- Woolworths、Kmart 等零售源
- 银行流水（如 CommBank）
- CSV 导入
- 发票 OCR 等增强录入

### 2.2 账单与条目（Bill / Entry）

一次获取或录入对应一张账单；账单下可有多条明细。

- 超市类：一次购物多条目（商品名、数量、单价、折扣等）
- 银行类 / 笼统流水：通常一条概括性条目

### 2.3 家庭成员（Person）

只承担两件事：

- 管理各数据源相关的 credential（登录/授权信息）
- 在 AA 中作为分摊身份（谁参与、占多少比例）

不做角色权限、可见范围等访问控制。

### 2.4 分类与标签

使用 **jev** 管理分类与标签，并挂到账单或条目上，用于筛选、汇总与（可选）辅助 AA。

### 2.5 AA 规则

按**数据源组合**配置：

- 哪些来源（或来源组合）下的账单需要 AA
- 参与成员及各自百分比

使用者以「账单从哪来」为主轴设定分摊，而不是先做复杂的权限或按人隔离账本。单笔覆盖等细化可在规则体系上扩展。

### 2.6 结算

在结算中心按周期套用 AA 规则，算出成员间应付/应收，支持标记已结清并保留历史。

### 2.7 去重与对账

同一笔消费可能同时出现在超市明细与银行扣款中。系统应支持匹配与去重，对未匹配或疑似重复的流水予以提示，避免汇总与 AA 被算两次。

## 3. 功能范围

### 3.1 纳入范围

| 能力 | 说明 |
|------|------|
| 多源账单管理 | 手动、Coles，以及后续零售/银行/CSV/OCR |
| 整合与可视化 | 日/周/月/季/年收支与结余；按来源、分类等维度 |
| 分类与标签 | 基于 jev |
| 家庭成员 | credential + AA 身份 |
| AA 规则 | 按数据源组合设定是否 AA 及分摊比例 |
| 结算中心 | 周期结算、结清状态、历史 |
| 去重对账 | 跨源匹配，突出未匹配/重复 |
| 预算与异常（增强） | 分类预算、超支与异常消费提示 |
| MCP（后期） | 向外部 Agent 开放查询/汇总等能力 |
| 投资（后期） | 与日常流水分离的投资相关能力 |

### 3.2 明确不在本项目内

- AI Agent 本体（如自动生成购物清单的 Agent 实现）
- 细粒度权限与多租户访问控制

---

## 4. 用户主流程（概念）

1. 配置家庭成员，并按需填写各源 credential  
2. 手动记账，或从 Coles（及后续源）同步账单  
3. 为条目补充/调整分类与标签（jev）  
4. 在可视化中查看各周期、各来源的收支结构  
5. 配置「哪些来源组合要 AA、每人多少」  
6. 在结算中心按周期生成应付关系并标记结清  
7. 借助去重/对账避免同一消费被重复计入  

后期可在此之上增加预算提醒、MCP 查询、投资视图等。

---

## 5. 里程碑

按完整项目分期；前期不做 MCP 与投资。

| 阶段 | 名称 | 内容 |
|------|------|------|
| **M0** | 基础骨架 | 应用可运行；核心概念落地为可扩展结构；Manual / Coles 接入位就绪 |
| **M1** | 手动记账 + 成员 | 手动账单与条目；成员的 credential 与 AA 身份 |
| **M2** | Coles 源 | Coles 同步接入（实现自填）；导入反馈与基础幂等 |
| **M3** | 分类与标签 | jev 体系；挂载到账单/条目；可筛选 |
| **M4** | 汇总可视化 | 多时间粒度收支结余；按来源、分类等维度 |
| **M5** | AA 规则 | 按数据源组合配置是否 AA 及成员百分比 |
| **M6** | 结算中心 | 周期结算、结清标记、历史 |
| **M7** | 去重与对账 | 跨源匹配；未匹配/重复提示（随银行等源完善） |
| **M8** | 更多数据源 | CSV、Woolworths、Kmart、银行等 |
| **M9** | OCR / 增强录入 | 发票识别与人工校正等 |
| **M10** | 预算与异常 | 分类预算、超支与异常提示（可选增强） |
| **M11** | MCP | 向外部 Agent 开放约定能力 |
| **M12** | 投资模块 | 与日常流水分离的投资能力 |
| **M13** | 产品化收尾 | 导出、备份、失败通知、部署与限制说明 |

**依赖关系简述：** M1 → M2 → M3 → M4 宜顺序推进；M5 → M6 紧耦合；M7 在银行等源（M8）就绪后价值更大，可先做同级去重骨架；M11、M12 明确后置。

---

## 6. 设计原则

- **来源优先：** 数据按 Source 接入，AA 也以来源组合为主要配置轴  
- **先记账、再分摊、再结算：** 流水完整优先于规则完备  
- **接口留白：** Coles 等平台细节由实现方填充，产品层只约定「能同步成账单与条目」  
- **敏感信息最小化暴露：** credential 仅服务取数与成员绑定，不做多余权限模型  
- **后期能力不堵前期：** MCP、投资、多源扩展不阻塞手动 + Coles 主路径  

---

## 7. 成功标准（项目层面）

- 家庭能把日常开销（至少手动 + Coles）收进同一处并看清结构  
- 能按来源组合完成 AA，并在结算中心闭环结清  
- 分类/标签可用 jev 支撑日常查询与汇总  
- 跨源重复记账可被发现或合并，汇总可信  
- 后续源、MCP、投资可在不推翻主模型的前提下追加
